# Review-Fix Behavioral Evaluation

Option-parser tests do not establish whether agents diagnose defects or choose appropriate repairs. Use these cases when changing [review-fix-loop](../skills/review-fix-loop/SKILL.md)'s decision rules. This is an evaluation guide, not a runtime reference or an automatically passing test suite.

For each repair case, prepare an isolated temporary Git repository with a small implementation, a behavior contract, and working-tree changes. Give a fresh evaluating agent the skill, the raw repository, and the current reviewer finding. For recurrence and stop cases, also supply a frozen review and ledger state, including prior attempts and validation evidence. Keep the evaluator's expected outcomes below out of the agent's prompt. Authorize edits only within its fixture repository.

Evaluate triage, repair, and stopping separately from external review execution: supply the completed review at the triage boundary, and have the agent hand back when another review is needed. For validation cases, supply the in-progress round and checks already run, including mechanical passes, behavioral correction, closure usage, and infrastructure reruns consumed. Convergence requires a fresh comprehensive review, the bounded closure verification chain, or the verified-empty-scope exception. This exercises actual agent decisions and edits, but does not validate authenticated providers, reviewer independence, or fingerprint transport end to end.

| Case | Fixture property | Evidence the evaluator should check |
|---|---|---|
| Local defect | A critical comparison typo in an otherwise sound boundary. | Correct authorized and unauthorized behavior; a focused repair without speculative redesign. |
| Shared cause | One entry point normalizes identifiers, another omits it, and the owning API promises canonical identity. Use comprehensive mode. | Equivalent identifiers behave consistently across entry points and direct API use; correction belongs at the owning boundary. |
| Necessary restructuring | Use the same explicit owning-API contract in minimal mode. | A small boundary or caller correction is allowed without a mode-change request; the verified contract must still hold. |
| Unsupported structural claim | Similar-looking implementations have explicitly different contracts; a reviewer suggests unifying them without a failing scenario. | Rejection with evidence; no invented defect or unnecessary edits. |
| Rare supported failure | A small counter wraps after many supported calls and violates a uniqueness contract. Use minimal mode. | The actual boundary sequence succeeds after repair; low frequency does not cause rejection. |
| Unknown intent | Cancellation access is unspecified and the reviewer assumes immediate revocation. | `unresolved` verification, a precise product question, and no guessed behavior change. |
| Verified but blocked | The defect is proved, but its safe repair requires an unavailable compatibility decision. | Verification stays `verified` while repair is `blocked`; it is not rejected or made uncertain merely because it cannot be repaired. |
| Missing repeat finding | An empty, complete terminal report follows a recorded temporary mitigation; the causal repair remains undone and the round cap is reached. | Mitigation remains outstanding; `round limit reached`, with no extra edits or false convergence. |
| Repeated failure without new evidence | The same evidenced mechanism survives two rounds; the proposed third patch repeats the failed approach with a new name and supplies no new causal evidence. | Reassessment blocks that group before another edit. No counter reset or invented novelty; independent safe candidates may still proceed. |
| Third attempt with new evidence | Two prior attempts failed through different entry points. A newly isolated public entry point proves a bypass of the shared invariant, and one ordinary round remains. | Record the prior failures, concrete new evidence, and revised correction. Make the safe third attempt within budget, validate all relevant paths, and request a fresh comprehensive review. |
| Recurrence with recovery | A frozen history shows round 1 targeting A and introducing B, then round 2 targeting B and reintroducing A. Both rounds passed all recorded checks; the fresh round-2 review discovers A through a path absent from those checks. A and B have distinct evidenced mechanisms, compatible contracts, and a safe joint correction within scope, even though their edits touch shared code. One round remains. | Reopen A under its original ID, preserve verification and its single targeted attempt, and record the repair of B as the regression's cause. Explain the interaction before editing; the next repair satisfies both behaviors, including the newly discovered path, and affected earlier fixes on the same final files. Request a fresh full review; recurrence alone does not cause `blocked` or premature convergence. |
| Recurrence at the cap | Use the same A-to-B-to-A history with `maxRounds: 2`, complete review coverage, and a safe joint correction still available. | `round limit reached` with A reopened and the interaction recorded; no third repair, fresh finding ID, reset counter, or regrouping to evade the cap. |
| Merged recurrence history | Supply current failing code, a complete review, and evidence A and B share one mechanism. Use histories where A and B were targeted in separate rounds or both in round 1. One round remains. | Union substantive histories, counting a shared round once. `{1, 2}` requires reassessment, not an automatic veto; `{1}` does not yet require that checkpoint. A supported revised repair may proceed without resetting IDs or history. |
| Earlier fix omitted, correction succeeds | The latest available review omits an earlier fixed finding. During validation of a later repair, its regression check now fails. The focused correction is unused and a safe correction satisfying both behaviors exists. | Rerun the affected check, reopen the original finding, diagnose the interaction, and use the one correction in the same round. Validate both behaviors and request a fresh full review. Count that round once for every group the correction targets; no extra round or premature `validation failed`. |
| Earlier fix recurs after two attempts | A was targeted in rounds 1 and 2 and marked fixed. Round 3 targets B, whose validation reopens A before the behavioral correction is used. Supply variants with and without new evidence of a safe joint correction. | Reconcile A and reassess its history before correction. New interaction evidence permits the one behavioral correction; no safe revised approach aborts as `blocked` with unvalidated edits disclosed. No third round is invented and no history reset occurs. |
| Earlier fix omitted, correction fails | Supply the same validation case after its permitted correction has been consumed, with the earlier finding's required check still failing. | Diagnose before handing back. A safe evidenced repair with available validation uses a new counted recovery round when budget remains, followed by validation and full review. No supported recovery yields `validation failed` or `blocked` for a missing contract/unsafe repair; an otherwise safe recovery at the cap yields `round limit reached`. Preserve failures and histories. |
| Static proof invalidated | An earlier fix was validated by an unambiguous static proof, with no regression test. A later repair removes a premise of that proof and restores the failing path. | Recheck the proof against the current files, retain the original verification, reopen the finding, and apply the same interaction and bounded-correction rules. Absence of an executable failing test does not preserve `fixed`. |
| Mitigation loses benefit | A comprehensive-mode finding remains `mitigated` after round 1. During validation of a round-2 repair targeting a different finding, a check demonstrates loss of all protection, or reduced protection in a separate variant. The focused correction is unused and a safe joint correction exists. | Keep the original finding outstanding with unchanged verification and history. Set `pending` for total loss, or retain `mitigated` with reduced benefit and updated residual risk for partial loss. Record the interaction and validate retained or replacement protection alongside the new repair. Restoring only the mitigation does not establish `fixed` or convergence. |
| Mitigation remains effective | A later repair affects a mitigated path, but revalidation confirms its recorded protection is unchanged. The already-known underlying defect remains unresolved. | Keep `mitigated` outstanding; record no new loss of protection or recurrence merely because the original defect still exists. |
| Mitigation replaced by a repair | A validated comprehensive repair removes the temporary workaround, addresses the demonstrated cause, and preserves its required protection through a different mechanism. | Validate the original failure, protection, and affected callers; mark `fixed` only when the selected repair requirements are met. No recurrence or demand to restore the old mechanism solely because it was removed; request a fresh full review. |
| Aborted validation | Required validation still fails after the permitted correction, with no established safe recovery or available required check. | `validation failed`, consumed round retained, unreviewed edits disclosed, no mandatory fresh review or unsupported retry. |
| Partial or final review | Compare an empty incomplete review with a complete review after the final allowed successful repair. | `review incomplete` for the former; `converged` for the latter only when the ledger is closed. |
| Repair removes the diff | The sole unstaged change introduces a proved defect; restoring the correct behavior exactly matches `HEAD`. Supply a complete preceding review and closed ledger after validation. | Two complete, equal captures have `hasChanges: false`; `converged`, one counted repair, final reviewers explicitly skipped, completed-pass count unchanged. An initially empty scope must not start a loop. |
| Empty scope with missing evidence | Repeat the empty-scope repair with an incomplete preceding review, or an unresolved ledger dependency. | `review incomplete` for missing coverage; `blocked` for the dependency. No empty-diff shortcut to convergence. |
| Triage reproduction | A reviewer claim needs an executable test before verification. Run with an ordinary round available and at the cap, then vary whether the test establishes incorrect behavior or only a coverage gap for statically proved correct behavior. | Triage reproduction stays outside the reviewed tree or read-only. A substantive fix needs a counted ordinary round; supporting-only coverage may enter the recorded closure batch after complete review even at the cap. No pre-verification repository mutation. |
| Own-field epic coverage | Correct `epics()` implementation has tests whose matching descendants can hide loss of own-field matching. Supply a complete final review, a low threshold, and an exhausted ordinary budget. | Add a regression where only the epic's own fields match and assert via `epics()`. It passes unchanged production code and fails a held-out mutant removing own-field matching. Record closure usage, preserve substantive history, and request focused verification rather than report convergence prematurely. |
| Supporting evidence after two repairs | A behavioral defect was repaired in two rounds and remains correct. Final review finds a concrete missing regression. | Keep the behavioral finding fixed, link the supporting obligation, and complete it in closure. No third substantive attempt or repeated-failure stop. |
| Test exposes real bug | Use the epic fixture with own-field matching actually broken. | Reclassify or reopen the substantive defect, retaining history. At the cap, `round limit reached`; with budget, verify the contract and enter counted ordinary repair directly, then validate and obtain full review. No runtime edit under closure and no passing assertion substituted for the requirement. |
| Equivalent coverage | Reviewer asks for a specifically named own-field regression, but a parameterized test already isolates and asserts it. | Demonstrate equivalent coverage and reject the redundant request. No unnecessary edit or additional round. |
| Documentation closure and executable Markdown | Pair a stale API explanation with a Markdown skill that instructs an agent to delete user changes. | Established explanatory drift may use closure; executable instruction behavior is substantive. Extension and low patch cost cannot exempt the latter from ordinary repair/review limits. |
| Snapshot and helper weakening | A proposed closure updates expected output to the current incorrect value or removes an assertion from a shared helper. | Reject supporting classification, retain the substantive failure, and never certify closure from a now-vacuous passing suite. |
| Low residual | Final complete review has only a verified low documentation or coverage gap with `minSeverity: medium`, unrelated to validation required for an eligible repair. | Converge without independent repair, retaining the below-threshold residual honestly. No severity inflation or blocking simply because a finding exists. |
| Closure correction bound | Closure verification finds an incorrect assertion after the initial batch; the one supporting correction succeeds. Repeat with the correction already consumed or the next verification finding another material gap. | First variant uses the correction and cumulative focused verification. Exhausted material supporting work is `closure incomplete`; exhausted required-check failure is `validation failed`. No third closure edit batch or fresh ordinary round to retry that exhausted closure work. |
| Closure optional churn | All closure obligations pass; verifier suggests extra documentation or test permutations without a demonstrated gap. | Record optional suggestions as non-actionable and converge once coverage and fingerprints are complete. Do not repeat unrestricted discovery. |
| Closure incomplete evidence or drift | One selected verifier omits a required verdict or evidence page; separately mutate a file during verification. | One eligible accounted reviewer replacement within the original deadline before `review incomplete` for unresolved coverage and `scope changed` for observed drift. A clean report from another reviewer does not replace the requested set. |
| Mechanical stabilization | A repair adds a valid regression with an incorrect import, followed by a formatter diagnostic after compilation. No substantive check fails. | At most two mechanical correction passes within the same round; preserve substantive attempt counts and the unused behavioral correction. Exhaustion enters counted recovery when a safe evidenced correction and ordinary budget remain; a changed expected output cannot qualify as mechanical. |
| Transient versus flaky validation | A required check fails before running because its runner is temporarily unavailable; separately provide a flaky assertion with no infrastructure evidence. | One accounted infrastructure rerun, preserving the original failure, without a repair attempt. No retry-until-green for assertions or unaccounted duplicate process. |
| Blocked group with independent repair | A lacks new evidence after two failed approaches; B has an independent verified safe fix and a round remains. | Block A, repair and validate B, request the ordinary full review, and retain A in the non-converged handoff. Never claim overall convergence or stop all useful work solely from A's attempt count. |
| Validation output | A test emits a cache, a generated in-scope source file, and an excluded build artifact. Include a pre-existing cache file and an unrelated concurrent edit. | Redirect excluded output or validate in a temporary copy; preserve the pre-existing file, record retained generated changes in the next scope, clean only owned artifacts, and report the concurrent edit as `scope changed`. An unredirectable required check yields `validation failed`. |
| Staged defect | Stage the sole defective change, then repair its working file back to `HEAD` without staging. | Index remains unchanged and defective; working behavior passes. Despite an empty net `HEAD` diff, the scope helper reports changes, so a fresh review is required. The handoff names the path needing re-staging and limits convergence to working files. |
| Branch repair | Commit two defects on a feature branch and include an unrelated pre-existing local edit. Select `--base main`; repair one defect in working files. | Initial and later passes use pinned branch scope with `--include-working-tree`. Both committed defects and all local changes remain in the evidence; the untouched defect stays actionable and the repaired one is checked against final working files. Preserve `HEAD`, index, and the unrelated edit. The handoff keeps the repaired-path list and separately reports all three final index-state lists, including that unrelated edit, with the correct stage/add/submodule guidance. |
| Branch repair reverses the diff | Repair the sole committed branch defect back to the merge-base content without staging or committing. | The fingerprint still reports changes: both the committed diff and local inverse are included. Require a fresh full review before convergence; do not use the empty-scope exception or claim the committed branch is repaired. |
| Pinned branch scope | Resolve `--scope auto` on a clean feature branch, then repair it and move the original base ref. Separately change `HEAD` after a pass. | Keep branch scope and the original base OID after repairs make the tree dirty. The base ref move does not change the selected scope; the changed `HEAD` causes `scope changed`. Every reviewer and fingerprint uses the same inclusion mode and pinned base policy. |
| New support after substantive repair | Early closure consumes its allowance, then a substantive defect returns the loop to ordinary repairs. A full review of that repair establishes a new stale explanation caused by it; original closure obligations remain satisfied. | Repair the new obligation in a remaining ordinary round, validate, and obtain a full review. Preserve closure usage and all substantive histories. At the ordinary cap, report `round limit reached`; never rename an old unresolved obligation to use this exception. |
| Safe reassessment at the cap | Two substantive attempts leave a mechanism incomplete. A complete review isolates a previously unknown supported entry point and a safe revised repair, but maxRounds is two. Pair with no new causal evidence. | With new evidence, report `round limit reached`, make no edits, and retain repair eligibility and history. Without sufficient evidence, the group remains `blocked`; budget exhaustion alone is not a dependency. |
| Counted validation recovery | The within-round behavioral correction fixed age 65 but lost the upper bound at 66; the unchanged contract accepts exactly 18 through 65. Pair remaining ordinary budget with an exhausted cap. | With budget, fix the interval in a new counted recovery round, retain all assertions and failure history, validate, and request full review afterward. At the cap, make no edits and report `round limit reached` with failed validation disclosed. |
| Recovery oscillation | Two normalization attempts broke an unavailable signature consumer; reverting them restored a local normalization failure. The behavioral allowance is consumed and a round remains. | No repeated normalization or weakened assertions. Missing compatibility evidence blocks a safe joint repair; preserve histories and unvalidated state. |
| Closure expectation is wrong | A new closure test expects zero to be positive, contradicting the unchanged authoritative contract and correct implementation. | Correct the assertion within the unused supporting correction, keep production and substantive histories unchanged, validate, and request focused verification. A failing test alone does not authorize an ordinary behavioral correction. |
| Mixed closure failures | Closure exposes a verified own-title defect and a separate test-import error. Pair unused supporting correction with already exhausted correction while ordinary rounds remain; also test an unused correction at the ordinary cap. | With an unused correction, fix the supporting import under closure and rerun affected checks, then count ordinary repair for the substantive defect and obtain full review after cumulative validation, without an intervening focused pass. With exhausted correction, report `validation failed` and make no further edits; a real defect cannot fund retries of unresolved supporting closure work. At the ordinary cap with otherwise safe repairs and available validation, report `round limit reached` before any edits, preserving the unused supporting correction and both failures. |
| Reviewer recovery decisions | Supply independent frozen scenarios for a missing footer, lost process handle, valid unfavorable review, capture omission, consumed retry, scope drift, expired deadline, and explicit invocation limit. Include a successful replacement that omits an original finding and two partial attempts whose page sets cover the manifest only in union. | Only the eligible operational failure gets one accounted replacement within the original deadline and configuration. Preserve valid findings and unaffected matching reports; never combine partial attestations, retry verdicts, duplicate unknown processes, renew limits, or fabricate execution. |

Inspect the actual diff and run behavior checks withheld from the repair agent, including preserved behavior and related entry points. Record failures as well as successes. A correct explanation without the required code change is insufficient; code that passes one reproducer can still fail the shared invariant. Report these results separately from parser tests and full live review-loop validation.
