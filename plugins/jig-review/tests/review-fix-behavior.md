# Review-fix verification

[controller-boundaries.test.mjs](controller-boundaries.test.mjs) checks unavailable-provider attempt accounting, repository-relative discovery from a subpackage, arbitrary filename dictionaries through persisted repair, original-source read denial and workspace-link leakage, capacity admission, and explicit settled-run pruning. Both CI platform jobs include these regressions. Sparse 12 GiB ignored artifacts exercise repair and isolated validation without consuming retention limits; a separate disk-availability test checks that low free space still stops allocation. Capacity tests exercise logical byte accounting; they do not claim a real Rust build, a filesystem quota, or a large-repository latency benchmark.

The executable lifecycle suite is [review-fix-controller.test.mjs](review-fix-controller.test.mjs). It runs the real controller against temporary Git repositories, subprocess reviewer/repair stubs, and real validation commands. Run it with:

```sh
node --test plugins/jig-review/tests/review-fix-controller.test.mjs
```

It checks complete repair and terminal review, provider fallback and strict failure, counted validation recovery, concurrent source mutation, staged/unstaged/untracked/submodule preservation, combined branch scope, persisted resume, duplicate invocation prevention, oscillation, a single contract question, missing acceptance evidence, native result immutability, locking, and contract tampering. Regression cases also cover zero-exit timeouts, rejected/threshold-filtered validation failures, harmless Git index refreshes versus staged changes, cancellation before worker claim, interruption and concurrent edits during application, existing ignored dependencies/build outputs, role environments, verbose logs, deduplicated file storage, and root validation discovery. CI includes this suite in the jig-review test glob.

[loop-platform.test.mjs](loop-platform.test.mjs) exercises real kernel locks, process identity and termination, sandbox write/cache/network boundaries, and Git metadata aliases. The controller and platform suites run on Linux and macOS in CI. macOS sandbox tests are required rather than skipped or replaced with host validation. On Linux, optional isolated-sandbox tests explicitly skip if Bubblewrap/user namespaces are unavailable; checkout validation and lifecycle tests still run. Those skips do not establish Linux sandbox support on that host.

These are lifecycle tests. The stubs do not establish model diagnosis quality, live provider availability, or whether a natural-language request is routed correctly by a particular host. For a live behavioral evaluation, give an isolated agent a repository and an ordinary “review and fix this” request, then inspect the resulting run record and source changes. Require acceptance evidence, complete reviews, validation results, and no routine approval questions. Run separate negative cases for review-only and explicitly one-pass requests. Paid provider execution needs existing authorization.

[loop-failure-boundaries.test.mjs](loop-failure-boundaries.test.mjs) interrupts allocation before assignment publication and worker startup before its command grant, and checks descendants after the command leader exits. It also exercises SHA-256 repositories/submodules, relative command execution, durable preparation failure, bounded triage/repair retries, and retained exit facts after forced stream cleanup. These tests run in both CI platform jobs; phase-boundary resume tests alone do not prove crash safety inside a transition.

The frozen-history loop cases in `evals/cases.json` describe the retired Markdown protocol, including its removed closure and nested budgets. They are marked `runtime: "markdown-loop-v1"`; current evaluation selection rejects them and exports report them separately from current coverage. Keep the fixtures as historical reproduction material; translate a case into a controller test or a new live evaluation before using it to assess current behavior. The two one-pass routing cases explicitly prohibit re-review.

Production instructions and runtime code must not contain held-out fixture names or their specific oracles. Deterministic test fixtures belong only under tests and evaluations.

Converted private-copy lifecycle cases probe sandbox availability only when they execute isolated validation. Rejection and preparation cases that finish before validation continue to run without Bubblewrap. Direct-checkout fixture paths are canonicalized so symlinked temporary roots, including macOS `/var`, refer to the same directory as the controller.

[acceptance-reconciliation.test.mjs](acceptance-reconciliation.test.mjs) checks that native and external reviewers receive applicable validation receipts, and that ordinary triage can resolve acceptance uncertainty without another review or validation execution. Original reports remain unchanged; resolutions bind to the assessed report, source, and validation executions. Negative cases retain rejected or blocked concerns, failed validation, and uncertainty from later reports or changed source. These protocol tests do not establish whether a model correctly judges test coverage. The validation reconciliation suite also exercises a result arriving between the polling guard and result consumption, so receipt writes follow reconciliation in either timing.

[source-reconciliation.test.mjs](source-reconciliation.test.mjs) injects checkout edits after the guard but before review, triage, and inline repair result capture. Completed work survives without a failed attempt; historical acceptance stays out of the new quorum. A staged edit at the same boundary still stops the run and preserves the changed index.

Failure-boundary tests interrupt review, triage, repair, and validation after persisting the command but before dispatch. Changed source or index state prevents any invocation; unchanged state resumes the original command once. These cases distinguish an unstarted command from a recorded launch that may already be executing.

The direct-checkout CLI case starts with a clean index, retains a rejected file-to-directory replacement, and checks that `advance`, `run`, and `status` return the saved outcome and recovery evidence with an explicit staging-inspection error. Reporting preserves the directory contents and index.

Restore-and-stop cases cover all direct/inline repair and restoration combinations after failed checkout validation. Recovery uses recorded mutations regardless of repair format, restores the preservation baseline without changing the index, and stops without fresh validation, review, or a convergence claim.

Direct-checkout and repository-copy tests reject setuid, setgid, and sticky bits on managed regular files, including unlisted repair paths and files present before admission. Permission rejection preserves on-disk edits and the Git index without recording a successful repair or validation. Legacy-release cases retain backup permission bits and unchanged journals while allowing release and subsequent admission under the original backup-verification semantics.

## Repair-policy validation

The option and installation tests check `minimal`, `balanced` (default), and `comprehensive` independently of reviewer policy. Controller tests initialize each mode through the CLI, resume through native review/triage/repair assignments, and check that the saved mode and full policy reach every role and the final status. The CLI-backed lifecycle also checks external assignment delivery. Runs use version 14; version-13 and earlier runs require their original controller, while settled records can still be released without migration. The role checks reject repair imperatives in read-only assignments. A failing-validation fixture verifies that reviewer prose and command output reach later assignments as evidence without entering their instructions. These tests establish policy transport and persistence, not model resistance to instruction injection or repair judgment.

For a live behavioral evaluation, use isolated repositories with the following contrasting cases. Derive expected results from the task contract and exercise real callers. Evaluate source changes and executable evidence; do not score matching policy phrases, a filled diagnosis field, or agreement with one exact reference patch. Keep original task inputs and evaluator checks separate from agent-authored tests. Run repeated trials when comparing policies, retaining failures and cost as well as successes. These scenarios specify future live evaluations; no live pass is implied by the controller tests.

| Case | Required evidence | Failure to detect |
|---|---|---|
| One caller bypasses an already sound boundary | The caller uses the existing boundary; other supported callers still work | Unnecessary redesign or a new parallel guard |
| Several entry points inherit a defective shared invariant | The owning boundary enforces the rule; original and neighboring caller cases pass | Fixing only the reported caller while another affected path still fails |
| A domain rule needs information absent from a generic utility | Enforcement stays with the domain owner; the utility remains valid for other domains | Pushing domain policy into the lowest/shared layer |
| A local patch passes the reproduction but leaves the responsible contract unsound | Independent caller or boundary checks expose the residual cause; the final repair closes it | Declaring convergence from the reproduction alone |
| A failed first repair disproves the initial diagnosis | The next attempt uses the new evidence and corrects the mechanism | Stacking exceptions around the rejected explanation |
| A demonstrated cause cannot be corrected within the permitted scope | Residual work remains actionable/blocked and the handoff distinguishes mitigation | Reporting a mitigation as a completed repair |

Minimal mode should keep the search focused while still repairing established causes. Balanced mode should expand when a causal connection is established. Comprehensive mode should investigate related recurrence exposure without treating superficial similarity as a structural defect. Judge both under-repair and unjustified expansion.

File-state regressions cover permission-only repairs, content-plus-mode repairs, directly executable new scripts, removing executable permissions, and rejecting mode-only creation. They execute real validators and compare index bytes before and after. Snapshot/copy tests cover tracked files replaced by directories in the root and initialized submodules, with matching Git diffs; a complete controller run repairs a script inside such a replacement directory.

Workspace repair tests cover native and external attribution results, additions, deletions, binary and empty files, captured candidates surviving copy cleanup, and rejection of unattributed, excluded, ignored, symlink, index, and special-permission changes. Attribution failures retain the offending paths in the run record, distinguishing ignored additions from unchanged source paths. File-to-directory repair proposals exercise bounded rejection, fresh-copy retry, and attempt exhaustion with tracked and untracked original files; source and index remain intact. New files are created under umasks `002`, `022`, and `077` to check permission normalization. Editor replacements preserve all existing permissions and pass direct script execution; explicit workspace modes cover intentional permission changes without file images or chmod. Failed native and external repairs check that partial edits do not mask provider errors, including native index changes and unsupported filter attributes; uncertain completion stops without retry. These tests also retain the legacy inline-edit checks.

`review-handoff.test.mjs` exercises export and CLI import, a triage-first repair with zero discovery assignments, required validation and two fresh terminal reports, unchanged index bytes and user notes, rejection of stale/malformed/excluded evidence, preservation of partial reviewer coverage and attribution, restart-safe immutable handoffs, and unchanged discovery for ordinary fresh runs. Injection-shaped report text remains data outside assignment instructions; this is a structural boundary test, not proof of model-level injection resistance.

Per-round commit tests exercise the default mode over real temporary Git repositories: separate round commits, retained failed-validation commits, stable full-range terminal reviews, branch base pinning, interrupted HEAD/index publication, and refusal to overwrite concurrent index/HEAD changes. Existing preservation fixtures explicitly select `--commit-mode none`. These checks verify controller behavior, not a claim that automated reviews find every code defect.
