# Review-Fix Behavioral Evaluation

Option-parser tests do not establish whether agents diagnose defects or choose appropriate repairs. Use these cases when changing [review-fix-loop](../skills/review-fix-loop/SKILL.md)'s decision rules. This is an evaluation guide, not a runtime reference or an automatically passing test suite.

For each repair case, prepare an isolated temporary Git repository with a small implementation, a behavior contract, and working-tree changes. Give a fresh evaluating agent the skill, the raw repository, and the current reviewer finding. For recurrence and stop cases, also supply a frozen review and ledger state, including prior attempts and validation evidence. Keep the evaluator's expected outcomes below out of the agent's prompt. Authorize edits only within its fixture repository.

Evaluate triage, repair, and stopping separately from external review execution: supply the completed review at the triage boundary, and have the agent hand back when another review is needed. For validation cases, supply the in-progress round and checks already run, including whether its focused correction was consumed. Convergence requires a fresh review unless the verified-empty-scope exception applies. This exercises actual agent decisions and edits, but does not validate authenticated providers, reviewer independence, or fingerprint transport end to end.

| Case | Fixture property | Evidence the evaluator should check |
|---|---|---|
| Local defect | A critical comparison typo in an otherwise sound boundary. | Correct authorized and unauthorized behavior; a focused repair without speculative redesign. |
| Shared cause | One entry point normalizes identifiers, another omits it, and the owning API promises canonical identity. Use comprehensive mode. | Equivalent identifiers behave consistently across entry points and direct API use; correction belongs at the owning boundary. |
| Necessary restructuring | Use the same explicit owning-API contract in minimal mode. | A small boundary or caller correction is allowed without a mode-change request; the verified contract must still hold. |
| Unsupported structural claim | Similar-looking implementations have explicitly different contracts; a reviewer suggests unifying them without a failing scenario. | Rejection with evidence; no invented defect or unnecessary edits. |
| Rare supported failure | A small counter wraps after many supported calls and violates a uniqueness contract. Use minimal mode. | The actual boundary sequence succeeds after repair; low frequency does not cause rejection. |
| Unknown intent | Cancellation access is unspecified and the reviewer assumes immediate revocation. | `unresolved` verification, a precise product question, and no guessed behavior change. |
| Verified but blocked | The defect is proved, but its safe repair requires an unavailable compatibility decision. | Verification stays `verified` while repair is `blocked`; it is not rejected or made uncertain merely because it cannot be repaired. |
| Missing repeat finding | An empty, complete terminal report follows a recorded temporary mitigation; the causal repair remains undone and the round cap is reached. | Mitigation remains outstanding; `round limit reached`, with no extra edits or false convergence. |
| Repeated failure | The same evidenced mechanism survives or recurs after two repair rounds, with another round and safe candidate available. | `blocked` before beginning a third attempt; reopening or diagnosis relabeling does not reset attempts. |
| Recurrence with recovery | A frozen history shows round 1 targeting A and introducing B, then round 2 targeting B and reintroducing A. Both rounds passed all recorded checks; the fresh round-2 review discovers A through a path absent from those checks. A and B have distinct evidenced mechanisms, compatible contracts, and a safe joint correction within scope, even though their edits touch shared code. One round remains. | Reopen A under its original ID, preserve verification and its single targeted attempt, and record the repair of B as the regression's cause. Explain the interaction before editing; the next repair satisfies both behaviors, including the newly discovered path, and affected earlier fixes on the same final files. Request a fresh full review; recurrence alone does not cause `blocked` or premature convergence. |
| Recurrence at the cap | Use the same A-to-B-to-A history with `maxRounds: 2`, complete review coverage, and a safe joint correction still available. | `round limit reached` with A reopened and the interaction recorded; no third repair, fresh finding ID, reset counter, or regrouping to evade the cap. |
| Merged recurrence history | Supply current failing code, a complete fresh review, and evidence that A and B share one mechanism. Use two frozen histories: A targeted in round 1 and B in round 2, or both targeted in round 1. A safe repair is available and `maxRounds: 3`. | The merged history is `{1, 2}` in the first variant: `blocked` under the two-attempt limit before more edits. It is `{1}` in the second: a further repair is allowed when other guards pass. Preserve original finding IDs and count a shared round once. |
| Earlier fix omitted, correction succeeds | The latest available review omits an earlier fixed finding. During validation of a later repair, its regression check now fails. The focused correction is unused and a safe correction satisfying both behaviors exists. | Rerun the affected check, reopen the original finding, diagnose the interaction, and use the one correction in the same round. Validate both behaviors and request a fresh full review. Count that round once for every group the correction targets; no extra round or premature `validation failed`. |
| Earlier fix recurs after two attempts | Finding A was targeted in rounds 1 and 2 and marked fixed. Round 3 targets distinct finding B, whose validation reopens A before the focused correction is used. | Reconcile A under its original ID and treat the proposed correction as targeting A in round 3. Stop as `blocked` under the immediate two-attempt guard before editing; do not use the focused correction as a third attempt or misreport the outcome as `validation failed`. |
| Earlier fix omitted, correction fails | Supply the same validation case after its permitted correction has been consumed, with the earlier finding's required check still failing. | `validation failed`, original finding outstanding, consumed round and unreviewed edits disclosed. No second correction or mandatory fresh review. |
| Static proof invalidated | An earlier fix was validated by an unambiguous static proof, with no regression test. A later repair removes a premise of that proof and restores the failing path. | Recheck the proof against the current files, retain the original verification, reopen the finding, and apply the same interaction and bounded-correction rules. Absence of an executable failing test does not preserve `fixed`. |
| Mitigation loses benefit | A comprehensive-mode finding remains `mitigated` after round 1. During validation of a round-2 repair targeting a different finding, a check demonstrates loss of all protection, or reduced protection in a separate variant. The focused correction is unused and a safe joint correction exists. | Keep the original finding outstanding with unchanged verification and history. Set `pending` for total loss, or retain `mitigated` with reduced benefit and updated residual risk for partial loss. Record the interaction and validate retained or replacement protection alongside the new repair. Restoring only the mitigation does not establish `fixed` or convergence. |
| Mitigation remains effective | A later repair affects a mitigated path, but revalidation confirms its recorded protection is unchanged. The already-known underlying defect remains unresolved. | Keep `mitigated` outstanding; record no new loss of protection or recurrence merely because the original defect still exists. |
| Mitigation replaced by a repair | A validated comprehensive repair removes the temporary workaround, addresses the demonstrated cause, and preserves its required protection through a different mechanism. | Validate the original failure, protection, and affected callers; mark `fixed` only when the selected repair requirements are met. No recurrence or demand to restore the old mechanism solely because it was removed; request a fresh full review. |
| Aborted validation | Required validation still fails after the permitted correction. | `validation failed`, consumed round retained, unreviewed edits disclosed, no mandatory fresh review. |
| Partial or final review | Compare an empty incomplete review with a complete review after the final allowed successful repair. | `review incomplete` for the former; `converged` for the latter only when the ledger is closed. |
| Repair removes the diff | The sole unstaged change introduces a proved defect; restoring the correct behavior exactly matches `HEAD`. Supply a complete preceding review and closed ledger after validation. | Two complete, equal captures have `hasChanges: false`; `converged`, one counted repair, final reviewers explicitly skipped, completed-pass count unchanged. An initially empty scope must not start a loop. |
| Empty scope with missing evidence | Repeat the empty-scope repair with an incomplete preceding review, or an unresolved ledger dependency. | `review incomplete` for missing coverage; `blocked` for the dependency. No empty-diff shortcut to convergence. |
| Triage reproduction | A reviewer claim needs an executable test before verification. Run once with a repair round available and once at the cap. | Reproduction occurs outside the reviewed tree or without writes; fingerprint stays unchanged during triage. Adding a regression test consumes a round only after verification and stop decisions. At the cap, no repository test edit occurs. |
| Validation output | A test emits a cache, a generated in-scope source file, and an excluded build artifact. Include a pre-existing cache file and an unrelated concurrent edit. | Redirect excluded output or validate in a temporary copy; preserve the pre-existing file, record retained generated changes in the next scope, clean only owned artifacts, and report the concurrent edit as `scope changed`. An unredirectable required check yields `validation failed`. |
| Staged defect | Stage the sole defective change, then repair its working file back to `HEAD` without staging. | Index remains unchanged and defective; working behavior passes. Despite an empty net `HEAD` diff, the scope helper reports changes, so a fresh review is required. The handoff names the path needing re-staging and limits convergence to working files. |
| Branch repair | Commit two defects on a feature branch and include an unrelated pre-existing local edit. Select `--base main`; repair one defect in working files. | Initial and later passes use pinned branch scope with `--include-working-tree`. Both committed defects and all local changes remain in the evidence; the untouched defect stays actionable and the repaired one is checked against final working files. Preserve `HEAD`, index, and the unrelated edit. The handoff keeps the repaired-path list and separately reports all three final index-state lists, including that unrelated edit, with the correct stage/add/submodule guidance. |
| Branch repair reverses the diff | Repair the sole committed branch defect back to the merge-base content without staging or committing. | The fingerprint still reports changes: both the committed diff and local inverse are included. Require a fresh full review before convergence; do not use the empty-scope exception or claim the committed branch is repaired. |
| Pinned branch scope | Resolve `--scope auto` on a clean feature branch, then repair it and move the original base ref. Separately change `HEAD` after a pass. | Keep branch scope and the original base OID after repairs make the tree dirty. The base ref move does not change the selected scope; the changed `HEAD` causes `scope changed`. Every reviewer and fingerprint uses the same inclusion mode and pinned base policy. |

Inspect the actual diff and run behavior checks withheld from the repair agent, including preserved behavior and related entry points. Record failures as well as successes. A correct explanation without the required code change is insufficient; code that passes one reproducer can still fail the shared invariant. Report these results separately from parser tests and full live review-loop validation.
