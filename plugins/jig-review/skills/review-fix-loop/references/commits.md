# Commit publication

`--commit-mode per-round` is the default; `--commit-mode none` preserves the working-tree-only workflow and its original index. Explicit “no commits” or “leave the fixes uncommitted” requests select `none`. This setting is independent of repair breadth and reviewer policy, and stays pinned when resuming a run.

Select `none` before initialization when unrelated local changes must remain uncommitted, and report that reason. Keep the user's checkout and preserve those changes in place. Do not obtain a clean commit run by creating another worktree, moving changes away, or committing unrelated work. An already initialized run retains its pinned mode; a refusal requires resolving the specific conflict rather than silently relocating or restarting it.

In `per-round`, existing included working changes become a baseline commit before discovery. Each completed repair becomes a separate commit before required validation. This also applies with isolated validation: publish the repair, then validate a private copy of that committed tip; failed checks leave the round commit in the original checkout. Imported reviews enter triage directly; any still-uncommitted reviewed work joins the first repair commit, or a baseline commit if no repair is needed. Failed validation leaves its commit in the series; recovery appends another. Incomplete repair assignments retain their visible edits without committing them. No empty commit is created for an unchanged tree. There is no amend, rebase, squash, push, or history rewrite. If later concurrent or validation-generated source changes need a second commit in an already-published round, publication stops with those edits preserved unless triage has allocated another counted repair round. It never creates an unbounded stream of checkpoint commits or silently amends a round.

Commit messages identify the round and its findings. Baseline messages identify the task. The controller publishes the reviewed working-file contents and executable bits, including when `core.filemode=false`, without changing that setting. Included pre-existing staged and unstaged work joins the commit; partial staging is intentionally replaced by the resulting committed tree. Choose `none` when that staging split must remain intact. Dirty excluded files, dirty submodules or changed gitlinks, and skip-worktree/assume-unchanged entries stop commit mode without silently switching modes. Unfinished merges, rebases, cherry-picks, and reverts must be completed or aborted before using commit mode; the controller does not complete another Git operation or discard its metadata. An existing HEAD and usable local Git author/committer identity are required. Clean initialized submodules remain supported. The controller does not provision identities, signing tools, or credentials.

## Stable review range

For working-tree scope (including auto scope on a dirty checkout), the base is HEAD at initialization. For branch scope, the base is the initial merge base of HEAD and the selected base. The controller pins that object ID once; movement of a named base branch does not move the boundary. Existing branch commits remain in the range. Supply `--base` when a dirty checkout's earlier branch commits must also be reviewed.

Review assignments contain `commitRange.base`, `tip`, and `range`, with committed-only branch scope. Review the full range, not only the most recent repair commit. Each round advances the tip while retaining the base. Required validation runs against the published commit, including for Git-aware checks. The two terminal reports must match the same final fingerprint and exact base-to-tip range, and the checkout must be clean. Subsequent repairs require fresh validation and reviews. A higher severity threshold still produces only `THRESHOLD_MET`, never a claim that the series has no issues.

## Publication and recovery

Repair agents edit source and keep Git metadata unchanged. The controller constructs the tree using a private index and creates the commit with Git plumbing (`commit-tree`), honoring `commit.gpgsign`. Git commit hooks do not run; put required checks in the pinned validation contract. The controller journals the parent, new commit, old/new index contents, and lock identity before publishing. It acquires the real index lock, updates the branch ref with the expected parent, then installs the prepared index. Source files are never reset by this operation.

An interrupted publication resumes from the same recorded commit, without creating a duplicate. Only the exact recorded old/new HEAD and index states are accepted. Changed source, an unexpected commit or branch, a newer index, or an unowned/changed index lock stops publication and preserves the journal. A crash between lock creation and recording its identity requires manual reconciliation; the controller never guesses ownership of an existing lock. `status.commitRecovery` exposes the retained journal. Inspect it and the actual repository before resolving a conflict; do not remove locks or overwrite newer work blindly. Unresolved publication prevents release, pruning, or a replacement run. Resume the original run after resolving the specific conflict. A run already marked blocked can finish publication recovery but retains its blocked verdict.

Status reports `commitMode`, `commits`, and `commitRange`. Earlier commits remain even if validation fails, the round limit is reached, or review is incomplete. Those outcomes do not certify the range as clean. Convergence certifies the final tip against the full accumulated change; it does not imply every intermediate round commit passes validation. Defects already corrected later in the range are not residual findings.
