# Storage admission and explicit pruning

Read for `STORAGE_LIMIT`, custom storage limits, archival, or an explicit pruning request. Review/fix authorization does not authorize pruning.

Configuration `storage` accepts positive integer byte limits: `maxSourceBytes` (default 1 GiB), `maxRunBytes` (4 GiB), `maxRetainedBytes` (8 GiB), and `minFreeBytes` (64 MiB). Source <= run <= retained limits are required. Source capture is bounded before storing each file. Retention limits count durable controller records (source blobs, patches, transcripts, journals, and backups), without following symlinks. Temporary assignment/validation workspaces and scratch output are outside those retention totals. Before allocating source copies, the controller estimates their source bytes plus metadata/output headroom and checks actual free space on both filesystems. Capacity failures record `STORAGE_LIMIT` and stop; they never prune data, consume another repair attempt, or relax fingerprints. These are conservative admission limits for controller allocations, not OS quotas on unrelated writers or arbitrary validation output. Full content checks remain at mutation and terminal boundaries.

Git ignore rules govern source capture: ignored, untracked `target/`, caches, and generated outputs are not source or patch inputs. Tracked files remain source even when an ignore pattern matches them. Diagnostic Rust builds may create tens of GiB in a private workspace without exhausting the evidence-retention limit; actual disk exhaustion can still stop subsequent allocations. Temporary workspaces are cleaned through the existing owned-workspace lifecycle after their writers settle. Do not prune a run's evidence merely because its disposable build output is large. Older controller versions counted all workspace bytes against retention; a reported 4 GiB run limit is distinct from a free-space failure.

Regular source files have no fixed 32 MiB admission cap. Capture, blob storage, workspace copying, and application use bounded-memory file reads with content verification. Unchanged and review-excluded files still count toward source/storage budgets and remain available to builds and mutation guards. Review evidence and parsed validation-discovery inputs have separate limits; increasing storage budgets does not enlarge those limits.

`node <skill>/scripts/review-fix-loop.mjs prune --run <exact-run-directory>` explicitly deletes that settled run's entire record, including source blobs, transcripts, patches, and settled backups, and its owned temporary workspace. This cannot be undone through the controller; archive the record first if needed. Active runs, pending cleanup, and unresolved application recovery are refused. Pruning is never automatic or implied by a review/fix request. Merely reaching a terminal state retains the full record.

Before release or archival, inspect the retained-backup obligations in [recovery.md](recovery.md).
