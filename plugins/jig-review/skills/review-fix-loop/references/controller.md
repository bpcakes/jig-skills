# Controller interface

Run `node <skill>/scripts/review-fix-loop.mjs <command>` on Linux or macOS with Node 22+ and Git 2.42+ (needed to locate system attribute policy). Linux uses `flock` and `/proc`; macOS uses Python 3's standard-library kernel locking and the system `libproc` process API. No packages are installed by the controller. Validation defaults to the repository's existing checkout, installed dependencies, toolchain, and normal caches. It is cooperative local execution subject to host permissions, not a hermetic sandbox. Missing tools or dependencies are failures, not skipped checks or permission to install anything.

## Start and resume

Settled runs publish a receipt in `active.json` only after process/workspace cleanup and application recovery are resolved. Version-2 receipts retain the expected backup hashes independently of the run format; admission and release recheck those backups, so settlement cannot waive a late write. Before replacing the active reference, admission saves any outgoing backup receipt in `retained-backups.json` and rechecks every retained receipt on each subsequent admission. These obligations survive later runs and removal of the latest active reference; only explicit pruning of the owning run retires its receipt. Archiving workflow metadata does not require loading it again, but any referenced backups must remain available and unchanged. A receipt with no backups permits archiving the entire settled record. The controller does not delete the record. For an older reference, including a version-1 receipt without backup evidence, use `node <skill>/scripts/review-fix-loop.mjs release --cwd <repository> --run <exact-run-directory>`. Release can inspect settled v4/v5/v6/v7 journals without resuming, migrating, or rewriting them. It refuses active work, another run's reference, pending cleanup, unresolved recovery, and unknown formats. Missing recovery metadata must be restored; an old record with unjournaled backups cannot establish safe settlement. Errors identify the retained record or backup. Release is distinct from destructive pruning.

```sh
node <skill>/scripts/review-fix-loop.mjs plan-validation --cwd /repository
node <skill>/scripts/review-fix-loop.mjs init --cwd /repository --contract /tmp/task-contract.json
node <skill>/scripts/review-fix-loop.mjs run --run /repository/.git/jig/review-fix/<id>
node <skill>/scripts/review-fix-loop.mjs advance --run /repository/.git/jig/review-fix/<id>
node <skill>/scripts/review-fix-loop.mjs status --run /repository/.git/jig/review-fix/<id>
```

Always use the returned run path; linked worktrees store the run under the common Git directory. Only one active run may exist for that repository. `run` drives the executable loop until a terminal outcome, an unanswered contract question, or a native assignment requiring a result. `advance` performs one durable transition or consumes/starts one assignment. Neither resets rounds or provider attempts. `status` reads recorded state; a terminal status describes the recorded fingerprint, not later checkout changes.

Repository capability checks precede run allocation and provider/validator execution. Unsupported files, named Git filters, nested repositories, shallow history, Git replacement refs, or active legacy `info/grafts` files stop initialization with the affected path and reason (`UNSUPPORTED_REPOSITORY`). These history overrides are rejected in the root and initialized submodules, including linked worktrees and packed refs, and rechecked on source guards and before copy allocation. Included paths’ ancestor directories are checked for nested `.git` files or directories even when their descendants are already tracked; indexed submodules remain separate supported repository boundaries. Empty or comment-only graft files are allowed. Git resolves the actual metadata location; object alternates alone cannot preserve shallow boundaries or grafted ancestry. The controller does not fetch missing history. Do not proceed or fall back to a different workflow. Other unsupported platform or repository states also fail explicitly; they are not permission to weaken guards.

`init` also accepts the loop options and `--config /absolute/config.json`. Configuration is explicit JSON:

```json
{
  "reviewers": [{"id": "codex"}],
  "timeoutMs": 300000
}
```

Defaults are `validationMode: "checkout"` and `validationSandbox: "host"`. `validationMode: "isolated"` opts into a private validation copy and selects Bubblewrap on Linux or Seatbelt (`sandbox-exec`) on macOS. Explicit `validationSandbox: "bubblewrap"` or `"seatbelt"` also implies isolated mode. Executable copies live outside the source checkout, under a durable per-run path in the system temporary directory. The sandbox hides or denies reads of original workspace source, permits the necessary read-only Git object stores, disables network access, and provides private writable home/cache/scratch paths. It does not copy ignored dependencies or construct a toolchain; use it only for an existing project workflow that supports this environment. Missing dependencies or a missing selected sandbox stop the workflow without fallback. Combining isolated validation with the host sandbox is unsupported and stops before run allocation; select checkout validation explicitly when using the existing prepared environment. Each run belongs to its original repository and host; resume it there.

Only available capabilities enter provider selection. Skipping an unavailable capability consumes no invocation or attempt ID; every counted reviewer attempt is a durable assignment. Strict policy still requires distinct available providers.

The existing checkout is not an unfiltered shell environment. Commands inherit a curated set of PATH, locale, proxy, home/cache, and common Java, Go, Rust, Node-version-manager, and Python-environment settings; the exact allowlist is `localEnvironment` in [job-runtime.mjs](../scripts/job-runtime.mjs). All commands force `CI=1` and `GIT_OPTIONAL_LOCKS=0`, including when the parent supplied other values. Review commands additionally inherit credentials/profile variables for their selected provider. `environmentFrom` maps roles (`review`, `triage`, `repair`, `validate`) to additional inherited variable names, for example `{"validate":["PYTHONPATH","CC","PROJECT_TEST_CONFIG"]}`. These names are otherwise omitted; this option does not override the forced CI/Git settings. Values are resolved at execution, not persisted in requests. Do not allow provider credentials into validation. Commands and transcripts must not print secrets.

A `codex` reviewer without `command` uses native host delegation. External providers require `command` with adapter argv; an unconfigured external provider is unavailable, never relabeled native Codex. The adapter reads the assignment as JSON from stdin and emits exactly one JSON result on stdout, and must start a fresh session for each assignment. Provider IDs must be selected by `--reviewers`. Optional `triageCommand` and `repairCommand` use the same protocol. The bundled comprehensive-review CLIs emit prose and are not directly compatible JSON adapters: a bridge must pass the task contract and convert a complete report into this schema without dropping findings or coverage limitations. Do not claim an external provider ran without a configured bridge executing it.

Capability preflight checks executable files using the command's working-directory and role-PATH rules. Relative adapter paths refer to the repository root, mapped into the assignment copy for execution, not the controller's invocation directory. Required triage/repair executables and the selected sandbox's platform/executable compatibility are checked before publishing an active run. Preflight does not guarantee later authentication or sandbox permission success; later preparation failures become durable outcomes. Balanced review attempts use configured provider order, rotating deterministically after failure; each slot has its own attempt cap. Strict excludes providers already represented in the current quorum and never downgrades to same-provider evidence. Models and profiles are assignment inputs; adapters must honor them. Provider-specific flags require explicit selection when that provider is not in the defaults: for example, `--claude-model` also needs `--reviewers claude,codex` under balanced policy.

Completed unsuccessful reports, including invalid JSON, consume an attempt. Triage and repair use the same `maxProviderAttempts` cap per logical assignment, with separate immutable attempt IDs; transport retries do not increment the repair round. Known-not-started infrastructure failures allow one recovery within that cap. Commands whose outcome is uncertain (including provider timeouts, interrupted execution, or lost results) are not replayed. These stop review as `REVIEW_INCOMPLETE`, triage/repair as `BLOCKED`, and validation as `VALIDATION_FAILED`, with the role and `EXECUTION_UNCERTAIN` reason recorded separately. Native error reports may include `execution: "uncertain"` when completion cannot be established; a plain native error declares a completed failed invocation. A local assignment ID is not an external provider idempotency guarantee.

A persisted uncertain validation receipt stops immediately, even for an optional check: it cannot enter ordinary failure triage, consume a repair round, or execute a later check. Known completed validation failures still permit counted repair recovery. Timeout and uncertain completion are recorded separately from successful process cleanup.

## Task contract

Create the JSON file outside the working tree. Example:

```json
{
  "goal": "Preserve an item's display order after rename",
  "acceptanceCriteria": [{"id": "order", "description": "Renaming preserves the current ordering"}],
  "nonGoals": ["Changing the sorting UI"],
  "compatibilityConstraints": ["Keep the existing public API"],
  "permittedBehaviorChanges": ["Correct ordering after rename"],
  "requiredValidation": [{"id": "unit", "argv": ["npm", "test", "--", "--runInBand"]}]
}
```

Validation commands are argv arrays, never implicitly interpreted shell strings. Optional relative `cwd` selects a subproject. A check's `timeoutMs` overrides the shared configuration timeout (default 300000 ms); both accept integers from 1 to 2147483647. Set longer check timeouts in the frozen contract when the repository needs them. The resolved timeout is recorded with each result. `optional: true` records a nonrequired check; at least one command must be required. Include formatter checks, build/type checks, affected tests, relevant integration checks, and locally available CI equivalents when repository evidence calls for them. The discovery command reports manifests, task runners, CI files, and package-script candidates; the host must resolve a concrete plan before `init`. No automatic dependency installation occurs. Manifest discovery uses bounded regular-file reads; relative symlinks may resolve only through included repository files. External, cyclic, special-file, or oversized targets stop with their path and reason before run allocation.

Every criterion needs evidence in every review report, referring to required validation IDs. A missing, uncertain, or unsatisfied criterion prevents convergence. The controller checks that evidence is present and that its referenced checks passed; the reviewer must assess whether the evidence actually proves the requirement.

Discovery normalizes every invocation directory to the repository root, exactly as initialization does. Candidate `source` and `cwd` paths are always repository-relative, including when invoked inside a package. Each validation receipt records its actual execution directory, workspace, source root, validation mode, and sandbox.

## Repair policy

`init --fix-mode minimal|balanced|comprehensive` selects investigation breadth; the default is `balanced`. This is independent of `--review-policy balanced|strict`, severity thresholds, and round/attempt budgets. The [skill's repair modes](../SKILL.md#repair-modes) describe their scope. All modes establish the failure mechanism and repair its responsible contract or boundary, with necessary caller changes and validation. Comprehensive mode adds active investigation of related mechanisms and recurrence exposure; minimal mode limits that search without treating a known residual cause as resolved.

Every review, triage, and repair assignment includes `fixMode` and the full saved policy in `instructions`. This applies to both native and external providers. Use existing finding/decision `evidence` and edit `reason` fields for concise causal evidence and scope justification; no new result fields are required. Fresh reviewers receive this policy but no prior findings or repair narrative. They assess residual causes and responsibility boundaries independently. Triage must keep a mitigation's residual cause actionable or blocked, even when current validation passes.

The controller preserves and delivers the policy; it cannot mechanically prove that a model's explanation or repair is causally correct. Review evidence must assess that claim against the source, affected callers, and validation. A populated explanation or matching policy vocabulary is not an acceptance check. `status` includes the selected `fixMode`. Resume uses the saved mode and policy; it accepts no mode override. Version-8 and earlier runs require their original controller rather than silently acquiring a different repair contract.

## Native assignments

Read the `assignment` object in the returned request file. For reviews, pass that object to a fresh isolated agent. It contains the frozen contract, concrete scope, exclusions, repository copy, provider settings, fingerprint, and machine-readable `resultSchema`; it contains no prior findings. Return the exact result envelope and enum values from that schema, including severity `critical`, `high`, `medium`, or `low` (not P0–P3). The repository copy has source contents, index state, pinned HEAD, and initialized submodule contents. Use the provided scope metadata and OIDs for inspection; the copy does not reproduce source branch names or remotes.

Save the result outside the checkout and submit it:

```sh
node <skill>/scripts/review-fix-loop.mjs submit --run <run> --assignment <id> --result /tmp/result.json
```

Each result includes `assignmentId` and `fingerprint`, copied from the assignment. Results must be JSON objects, are immutable, and are accepted only for the current native assignment. Malformed persisted reports consume a failed attempt rather than preventing resume. A worker and pre-start cancellation or failure compete for one durable, exclusively published claim. A pre-start settlement stores its full outcome in that claim; the result file is a recoverable projection, so interruption between claim publication and result persistence cannot be mistaken for executed work. Cancellation can settle an unstarted assignment without executing it; a late worker cannot launch it. Pre-claim worker starts have a persisted budget (one start plus the infrastructure retry allowance) and one startup deadline shared by the controller, worker, and identity probes. `startupTimeoutMs` defaults to 5000; resuming never extends an already recorded deadline. The worker publishes an owned supervisor identity before granting command execution. That supervisor anchors the command group after the command leader exits, records exit and stream outcomes, and terminates the group before cleanup can complete. Controller interruption leaves claimed work running; worker loss closes the supervisor control channel and cancels its command. Do not manually rerun a claimed job. Lost results produce incomplete evidence, never assumed success or automatic replay.

The controller retains the open descriptor owning its repository lock. A short-lived `flock` or Python helper acquires the lock through a duplicated descriptor and must exit successfully within five seconds before work starts. Helper exit cannot release the controller's lock; returning, throwing, or controller death releases it. No long-lived helper's liveness is required for exclusion.

Process identity uses start times and boot identity on both platforms. Command results and process cleanup are separate obligations. A surviving group enters a durable cleanup wait; its saved result and assignment are retained without another provider invocation. `cleanupTimeoutMs` defaults to 5000, measured from the first remaining-group observation and never reset on resume. Both startup and cleanup timeouts accept integers from 1 to 2147483647. Group disappearance allows normal result consumption; deadline exhaustion stops with `cleanupBlocked`. Inspection failures during advancement stop durably when the journal remains readable and writable; they never establish process exit. Terminal outcomes and known cleanup obligations are persisted before cancellation or resource inspection, and resume repeats that cleanup without replaying jobs. A cleanup inspection error retains the terminal verdict, records `cleanupBlocked`, and prevents settlement or new-run admission until resolved. Keep advancing while `waiting` is true unless `cleanupBlocked` is reported. The controller never signals an unverified group. Resume cleanup on the original host after inspection and process cleanup are possible; a terminal failure is not retroactively promoted to success. Cooperative job isolation does not contain programs that deliberately leave their process group.

Review result:

```json
{
  "assignmentId": "<id>", "fingerprint": "<hash>", "complete": true,
  "findings": [{"key": "stable-causal-key", "path": "src/items.ts", "severity": "medium", "title": "Rename changes order", "evidence": "Concrete supported trigger and source reference"}],
  "acceptance": [{"criterionId": "order", "status": "unsatisfied", "evidence": "Source and test evidence", "validationIds": ["unit"]}]
}
```

Acceptance status is `satisfied`, `unsatisfied`, or `uncertain`. Findings must use stable causal keys and repository-relative included paths. Repeated findings retain the highest reported severity regardless of report order; individual reports remain available. Reports with findings or unmet requirements are still valid completed reviews; they are not provider failures to retry. Return `{"error":"reason"}` for a failed native invocation. External provider JSON cannot supply `exitCode` or `signal`: the worker records those transport facts. An `execution` field is accepted only on error results as `completed` or `uncertain`; uncertainty stops without replay. Reserved fields are rejected before merging provider data with transport metadata.

Triage result:

```json
{"assignmentId":"<id>","fingerprint":"<hash>","decisions":[{"id":"<finding-id>","status":"actionable","evidence":"Verified reproduction or source evidence"}]}
```

Decisions must cover every persisted finding, including earlier findings absent from fresh reports. Status is `actionable`, `rejected`, `fixed`, or `blocked`; `fixed` requires current validation. Mark only independently safe repairs actionable when other findings are blocked. The controller performs eligible repairs before stopping for remaining required or in-threshold blockers; below-threshold findings remain recorded without preventing `THRESHOLD_MET`. A material unresolved contract choice may instead return `question: {"text":"...","recommended":"...","evidence":"Repository evidence cannot decide because ..."}`. The controller returns this question once and waits. Record the user's answer with `answer --run <run> --text <answer>`; the text is literal, including a leading `--` (for example, `--text "--legacy should stay"`). Empty answers are rejected. The original contract remains frozen and its answer supplement is included in subsequent assignments. Routine approval questions are outside this protocol.

Repair result (preferred):

```json
{"assignmentId":"<id>","fingerprint":"<hash>","workspaceEdits":[{"path":"src/items.ts","reason":"Restore order while keeping the supported API","findingIds":["<finding-id>"]}]}
```

Edit files directly under the repair assignment's `repository` using the normal editing tool (`apply_patch` when available). Inspect the resulting diff, then return the attribution list above. Include additions and deletions; request intentional permission changes with an optional `mode` of `"0644"` or `"0755"` on the workspace edit. Every changed source path must be listed exactly once, and every listed path must have changed or request a mode different from its original mode. Attribution errors record both changed-but-unlisted and listed-but-unchanged paths. Keep result JSON and scratch scripts outside the copy and stop editing before submitting. Do not create replacement-building scripts or serialize whole source files for ordinary repairs. The controller captures the candidate when it consumes the result and preserves it in the blob store before cleaning up the copy. Review and triage assignments remain read-only.

For workspace repairs without an explicit `mode`, new files are normalized to `0755` if any executable bit is set, otherwise `0644`, regardless of the editor's umask. Existing files keep all their original permissions, so an editor's temporary replacement cannot widen read permissions or remove executable bits. An explicit workspace `mode` overrides these defaults for existing or new regular files, and can request a permission-only change without modifying the copy. Modes on deletions are rejected. Special permission bits in the copy are rejected. The controller also rejects unattributed changes, symlinks, ignored/unmanaged paths, exclusions, and changes to the Git index or pinned repository state before publication. Ignored diagnostic outputs are not part of the candidate.

Legacy inline `edits` results remain supported for adapters that supply file images without modifying their assignment copy. These results cannot be combined with `workspaceEdits`. Each inline edit has `path`, `reason`, `findingIds`, and complete replacement `content`, or `delete: true`. Regular-file edits accept an optional `mode` string of `"0644"` or `"0755"`. Include it with `content` to create an executable script or change contents and permissions together. For a permission-only repair of an existing included regular file, omit `content` and supply `mode`; its bytes are preserved. For example:

```json
{"assignmentId":"<id>","fingerprint":"<hash>","edits":[{"path":"scripts/check.sh","mode":"0755","reason":"The required validation directly executes this script","findingIds":["<finding-id>"]}]}
```

Modes with special bits or other permission values, modes on deletions, and mode-only edits of missing or excluded files are rejected. Permission changes participate in candidate identity, validation, recoverable application, and no-progress checks just like content changes. The Git index remains unchanged.

Use `delete: true` instead of `content` for a necessary deletion. The runtime enforces the published result schema before interpreting successful reports: both fields together, unknown fields, and invalid variants consume a failed attempt without constructing a candidate. Every path must cite verified actionable findings. When `mode` is omitted, replacements preserve the original permissions and new files default to `0644`. The controller rejects symlink edits, excluded paths, duplicate paths, unsafe paths, and candidate files hidden by Git ignore rules. Ignore-file changes are checked as part of the whole candidate before publication; already tracked files remain managed despite ignore patterns. Repairs are recorded as content-addressed candidates, not staged in the Git index. By default they are applied before validation and failed candidates remain in the checkout; recovery receives their patch and failure history and consumes another round. In explicitly isolated mode failed candidates stay outside the checkout. Returning the same file state or an earlier state terminates with no progress or oscillation, with one exception: after an applied checkout candidate fails required validation, an explicitly proposed, causally attributed repair returning exactly to the original contents may consume a recovery round. It uses the normal guarded application journal and stops `BLOCKED` with code `RESTORED_ORIGINAL`, without further review or a claim of convergence or fresh validation of the restored state. Interruption preserves this restore-and-stop decision; concurrent source/index changes still stop application.

## Validation and application

Review and triage copies keep Git-visible source read-only. Repair copies allow source edits reported through `workspaceEdits`; inline `edits` still require unchanged source. All assignments keep semantic index state and Git metadata read-only. Diagnostic commands may create ignored build/cache outputs; these are not source mutations or required-validation evidence. Other scratch files belong outside the copy. Successful results with unauthorized source or index changes are rejected with `ASSIGNMENT_CHANGED`; invalid workspace attribution also rejects the assignment. Explicit provider failures are recorded before copy inspection, preserving their error and execution status even when partial work makes the copy uninspectable. Rejections consume the normal bounded attempt, using a fresh copy on retry. An uncertain invocation still stops without replay. Real checkout drift retains its separate terminal `SCOPE_CHANGED` outcome.

Validation receives EOF on stdin; JSON stdin is reserved for provider assignments. Waiting on a claimed command reads job metadata, not source inventories. Full source and fingerprint guards run before starting unclaimed work, consuming results, applying changes, and terminal decisions. Drift during a running command is rejected at its result or worker-loss boundary, not continuously polled.

An unstaged tracked-file replacement such as `tool` becoming `tool/index.sh` is captured as deletion of the old tracked file plus the replacement tree's included files. Copies preserve those contents and the original index; directories are not regular-file repair destinations. A workspace repair that introduces a file-to-directory conversion is rejected as a bounded assignment failure before candidate publication; a retry receives a fresh copy. Attribution diagnostics identify ignored or unmanaged paths separately from unchanged paths and explain how to keep generated outputs outside the candidate.

Repository copies pin supported Git normalization settings, local/global/system attributes, and ignore policy for each initialized repository. Their staged and unstaged diffs must match the saved source before review. Inherited Git repository/index/object redirection is removed. Configured executable filter or text-conversion attributes are unsupported and fail explicitly; the controller does not transplant arbitrary Git configuration or provision conversion tools. Git policy changes participate in the source guard.

Validation executes the pinned commands against the actual candidate, in the existing checkout by default. Commands may write ignored build outputs and normal external caches, but may not alter source inputs or staged content. Include generated source changes in the repair result. Source/index drift during checkout validation consistently ends `SCOPE_CHANGED`, cancels active work, and retains the check's outcome and scope-change context; it does not presume whether the validator or another editor wrote the change. The controller never installs dependencies. Known-not-started startup failures, including log creation and process launch, allow one recorded infrastructure retry. Signal-terminated commands are failed checks for diagnosis, not automatically infrastructure failures. Required checks are non-waivable obligations: triage may propose a counted repair or report a blocker, but rejection and severity filtering cannot authorize another unchanged failing validation cycle. Success requires a `succeeded` outcome, exit zero, and no error or termination signal. Timeout and cancellation remain failures even if a signal handler exits zero. Validation stdout uses a bounded 8 MiB log plus a 16 Ki-character tail, with truncation disclosed; verbose output does not kill the check. Short writes are completed; zero-progress writes and log write/close errors after command launch stop without replay. Structured provider reports retain their separate 2 MiB transport limit.

Isolated validation retains read-only access to Git object alternates, including linked/shared repositories under temporary paths. Bubblewrap explicitly binds those object stores after concealing host `/tmp`; it does not grant source or object-store write access. This is Git access, not dependency provisioning.

Application rechecks each destination and moves an existing file to a journal-owned backup before publishing its replacement through exclusive creation. It never renames a candidate over a live destination. A concurrent new destination stops publication without overwriting it; displaced inodes remain recoverable, including writes through already-open descriptors. Backups and targets must share a filesystem. Recovery handles the interruption between displacement and publication, during which a path can be absent. The journal retains before/after content and displaced files. There is no automatic rollback over concurrent work and no claim of a multi-file transaction or exclusive ownership against unrelated editors.

The same-filesystem requirement is checked before run allocation/review, on source guards, and for every destination in a batch before any file is published. Cross-filesystem linked worktrees or mounted destinations stop with `UNSUPPORTED_REPOSITORY`; they do not proceed to a partial repair or get mislabeled as source drift.

Application, failure cleanup, resume, and new-run admission use the same temporary-content verification and recovery checks. Existing candidates are never truncated; only verified images may be reused or removed. Changed or uninspectable temporaries are retained in `applicationRecovery.retainedTemporaries`. Missing displaced replacement destinations and changed backups are reported in `applicationRecovery.unresolvedPaths`. Until these obligations are resolved, a new run is refused even after a terminal outcome. Recover retained work explicitly and resume; the controller will not automatically restore a path that another editor may have deleted after publication. Backups and unrelated files remain preserved.

Successful publication appends its displaced-file records to `completedApplications` in the same durable update that clears the pending apply. These records protect late writes through old descriptors across every repair round. Completed records check backups, not current destinations, which later repairs or user edits may legitimately change. Changed, missing, uninspectable, or unjournaled backups prevent convergence, settlement, admission, release, and pruning. A historical terminal verdict is not rewritten after a later mutation; status exposes the new recovery obligation and admission is refused. These are checkpoint checks, not exclusive locks against unrelated writers.

Private repository copies use an empty Git initialization template and explicitly create their required administrative directories. Every copy-preparation Git command disables hooks with `-c core.hooksPath=/dev/null`; each root/submodule copy also stores that local policy for subsequent Git operations. User templates and globally configured hooks cannot execute during preparation. The original checkout and global hook configuration remain untouched; pinned source comparison attributes and ignore policy are restored separately.

Validation scratch is reserved before allocation under the external workspace root, just like a repository copy. Both sandboxes route `HOME`, XDG cache/config, and temporary-directory variables to this resource on the workspace root's filesystem. Bubblewrap binds it through the concealed `/tmp` mount. Commands share scratch within a validation cycle; recovery cycles get fresh scratch. Each cycle queues both resources for cleanup after command settlement on success, failure, and terminal cancellation. Resume reclaims abandoned reservations and retries interrupted cleanup without replaying validation. Active scratch from older records is also eligible for exact-path cleanup; unreferenced historical scratch remains part of the retained record until explicit pruning.

The controller does not write the source index. Its guard compares staged OIDs, paths, modes, stages, and semantic flags, not cached inode/mtime fields. Ordinary `git status` refreshes are allowed in source and reviewer copies; staging changes are not. Preserve the original index and HEAD without treating Git's harmless internal cache updates as source edits.

This is cooperative workflow isolation, not a sandbox for adversarial model code. Native reviewers must remain read-only; the controller detects changes to source and assignment copies. Both platform sandboxes confine validation writes, but read-only host files remain visible. Non-UTF-8 paths, unmerged indices, files over 32 MiB, and symlink repairs fail explicitly. Git metadata path components are rejected regardless of case, including on case-insensitive macOS volumes. Snapshots and application do not manage ignored files; checkout validation may write ignored outputs as part of the existing workflow. Pre-existing excluded and submodule files participate in mutation guards even though they are outside repair scope.

## Artifacts and handoff

Version-9 `run.json` is authoritative workflow metadata. It pins the workspace-edit repair contract, `options.fixMode`, and the complete `fixPolicy` text at initialization; older controllers must not resume it without these requirements. Large immutable inventories use `$manifest` references into `manifests/`; their file entries reference SHA-256 content in `blobs/`. Resume loads and verifies inventories only when needed, so polling does not read or rewrite them. `events.jsonl` and `validation.json` remain projections reconstructed from the run. The run also contains contracts, reports, assignments, snapshots, patches, validation logs, and displaced-file `backups/`. `resources/` durably records copy and scratch ownership before allocation, including candidate-inspection and validation copies at the external `workspaceRoot`. Assignment identity and counters are saved before preparation; interrupted preparation resumes the same assignment without another provider attempt. Resume reconciles abandoned reservations and repeats pending deletion safely. Result consumption and cleanup responsibility are saved before deleting completed copies; source snapshots remain reconstructible from manifests and blobs. Snapshots retain each repository's Git object format and comparison policy, including initialized submodules. State uses atomic replacement, durable writes, and private permissions. Keep the record for resume and diagnosis; it includes source contents and provider transcripts. Older runs require the controller that created them and are not silently migrated, reinterpreted as source drift, or restarted. This run-format version is separate from the plugin release version. The controller does not commit, stage, push, or deploy.

## Storage admission and explicit pruning

Configuration `storage` accepts positive integer byte limits: `maxSourceBytes` (default 1 GiB), `maxRunBytes` (4 GiB), `maxRetainedBytes` (8 GiB), and `minFreeBytes` (64 MiB). Source <= run <= retained limits are required. Source capture is bounded before storing each file. Controller allocation boundaries count retained records and external copies without following symlinks, include metadata/output headroom, and check free space on both filesystems. Capacity failures record `STORAGE_LIMIT` and stop; they never prune data, consume another repair attempt, or relax fingerprints. These are conservative admission limits for controller allocations, not OS quotas on unrelated writers or arbitrary validation output. Full content checks remain at mutation and terminal boundaries.

`node <skill>/scripts/review-fix-loop.mjs prune --run <exact-run-directory>` explicitly deletes that settled run's entire record, including source blobs, transcripts, patches, and settled backups, and its owned temporary workspace. This cannot be undone through the controller; archive the record first if needed. Active runs, pending cleanup, and unresolved application recovery are refused. Pruning is never automatic or implied by a review/fix request. Merely reaching a terminal state retains the full record.

Report the outcome succinctly and link the run directory. Re-staging guidance describes final working files; it does not authorize staging. For dirty submodules, perform any separately authorized staging in the owning repository, from the innermost submodule outward. A skipped optional check remains visible. A failed or skipped required check, a missing acceptance criterion, an incomplete reviewer quorum, or an unmatched fingerprint prevents `CONVERGED`.
