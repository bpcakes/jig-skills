# Recovery and preservation details

Read when admission is refused, execution is uncertain, cleanup or application recovery is pending, repository capability checks fail, or preservation internals need inspection. Keep the existing run; never bypass a guard or replay uncertain work. Storage limits and deletion are covered in [storage.md](storage.md).

Settled runs publish a receipt in `active.json` only after process/workspace cleanup and application recovery are resolved. Version-2 receipts retain the expected backup hashes independently of the run format; admission and release recheck those backups, so settlement cannot waive a late write. Before replacing the active reference, admission saves any outgoing backup receipt in `retained-backups.json` and rechecks every retained receipt on each subsequent admission. These obligations survive later runs and removal of the latest active reference; only explicit pruning of the owning run retires its receipt. Archiving workflow metadata does not require loading it again, but any referenced backups must remain available and unchanged. A receipt with no backups permits archiving the entire settled record. The controller does not delete the record. For an older reference, including a version-1 receipt without backup evidence, use `node <skill>/scripts/review-fix-loop.mjs release --cwd <repository> --run <exact-run-directory>`. Release can inspect settled v4–v12 journals without resuming, migrating, or rewriting them. It refuses active work, another run's reference, pending cleanup, unresolved recovery, and unknown formats. Missing recovery metadata must be restored; an old record with unjournaled backups cannot establish safe settlement. Errors identify the retained record or backup. Release is distinct from destructive pruning.

Repository capability checks precede run allocation and provider/validator execution. Unsupported files, named Git filters, nested repositories, shallow history, Git replacement refs, or active legacy `info/grafts` files stop initialization with the affected path and reason (`UNSUPPORTED_REPOSITORY`). These history overrides are rejected in the root and initialized submodules, including linked worktrees and packed refs, and rechecked on source guards and before copy allocation. Included paths’ ancestor directories are checked for nested `.git` files or directories even when their descendants are already tracked; indexed submodules remain separate supported repository boundaries. Empty or comment-only graft files are allowed. Git resolves the actual metadata location; object alternates alone cannot preserve shallow boundaries or grafted ancestry. The controller does not fetch missing history. Do not proceed or fall back to a different workflow. Other unsupported platform or repository states also fail explicitly; they are not permission to weaken guards.

Completed unsuccessful reports, including invalid JSON, consume an attempt. Triage and repair use the same `maxProviderAttempts` cap per logical assignment, with separate immutable attempt IDs; transport retries do not increment the repair round. Known-not-started infrastructure failures allow one recovery within that cap. Commands whose outcome is uncertain (including provider timeouts, interrupted execution, or lost results) are not replayed. These stop review as `REVIEW_INCOMPLETE`, triage/repair as `BLOCKED`, and validation as `VALIDATION_FAILED`, with the role and `EXECUTION_UNCERTAIN` reason recorded separately. Native error reports may include `execution: "uncertain"` when completion cannot be established; a plain native error declares a completed failed invocation. A local assignment ID is not an external provider idempotency guarantee.

A persisted uncertain validation receipt stops immediately, even for an optional check: it cannot enter ordinary failure triage, consume a repair round, or execute a later check. Known completed validation failures still permit counted repair recovery. Timeout and uncertain completion are recorded separately from successful process cleanup.

Each result includes `assignmentId` and `fingerprint`, copied from the assignment. Results must be JSON objects, are immutable, and are accepted only for the current native assignment. Malformed persisted reports consume a failed attempt rather than preventing resume. A worker and pre-start cancellation or failure compete for one durable, exclusively published claim. A pre-start settlement stores its full outcome in that claim; the result file is a recoverable projection, so interruption between claim publication and result persistence cannot be mistaken for executed work. Cancellation can settle an unstarted assignment without executing it; a late worker cannot launch it. Pre-claim worker starts have a persisted budget (one start plus the infrastructure retry allowance) and one startup deadline shared by the controller, worker, and identity probes. `startupTimeoutMs` defaults to 5000; resuming never extends an already recorded deadline. The worker publishes an owned supervisor identity before granting command execution. That supervisor anchors the command group after the command leader exits, records exit and stream outcomes, and terminates the group before cleanup can complete. Controller interruption leaves claimed work running; worker loss closes the supervisor control channel and cancels its command. Do not manually rerun a claimed job. Lost results produce incomplete evidence, never assumed success or automatic replay.

The controller retains the open descriptor owning its repository lock. A short-lived `flock` or Python helper acquires the lock through a duplicated descriptor and must exit successfully within five seconds before work starts. Helper exit cannot release the controller's lock; returning, throwing, or controller death releases it. No long-lived helper's liveness is required for exclusion.

Process identity uses start times and boot identity on both platforms. Command results and process cleanup are separate obligations. A surviving group enters a durable cleanup wait; its saved result and assignment are retained without another provider invocation. `cleanupTimeoutMs` defaults to 5000, measured from the first remaining-group observation and never reset on resume. Both startup and cleanup timeouts accept integers from 1 to 2147483647. Group disappearance allows normal result consumption; deadline exhaustion stops with `cleanupBlocked`. Inspection failures during advancement stop durably when the journal remains readable and writable; they never establish process exit. Terminal outcomes and known cleanup obligations are persisted before cancellation or resource inspection, and resume repeats that cleanup without replaying jobs. A cleanup inspection error retains the terminal verdict, records `cleanupBlocked`, and prevents settlement or new-run admission until resolved. Keep advancing while `waiting` is true unless `cleanupBlocked` is reported. The controller never signals an unverified group. Resume cleanup on the original host after inspection and process cleanup are possible; a terminal failure is not retroactively promoted to success. Cooperative job isolation does not contain programs that deliberately leave their process group.

## Source reconciliation

At safe checkpoints, source-file edits with unchanged Git metadata are recorded and reconciled within the current run. Finish consuming an already-issued read-only assignment, keeping its original fingerprint as historical evidence. Keep its findings and proposed repair as historical evidence, then assess current applicability using the latest files. Disjoint repairs can be rebased mechanically; overlapping proposals are retained in `reconciliations/<n>.json` and returned to triage, never applied over newer edits. Path overlap identifies what to inspect, not whether a finding is still valid.

For legacy inline or explicitly isolated proposals, when triage is needed for a retained disjoint repair, its read-only copy includes that repair combined with the latest source changes. Assess the combined source, then validate the retained candidate without another repair round. Superseded proposals that never entered validation or publication do not count as attempted states for oscillation detection; previously validated or published states remain protected.

Every retained edit must still have an in-threshold `actionable` or `needs-validation` finding supporting its attribution. If any edit loses that support, archive and discard the whole proposal, then reassess the actual checkout; do not automatically splice a patch whose edits may depend on one another. Provisional dispositions based on the discarded candidate return to unresolved. Already-issued repair attempts still count, and any newly justified repair uses the remaining budget. A rejected co-attribution does not invalidate an edit that another supported finding still justifies.

When a subsequent source reconciliation invalidates provisional dispositions, return those findings to triage before validation, even if the new edits touch unrelated paths. Passing validation does not substitute for the invalidated assessment.

Match triage validation evidence to the actual assignment contents, including a retained candidate, as well as the current fingerprint. Restoring a previously validated checkout does not validate a different, unapplied candidate. When reconciliation changes assignment roles, the new role gets its own retry counter; prior attempts and repair rounds remain recorded, and repeated failures within the same role retain their limit.

Reconciliation preserves pending validation separately from pass/fail acceptance. Checks without accepted reuse remain pending, including optional checks that have not started or were marked for rerun. Older results cannot satisfy those pending checks even if the source returns to identical contents. Once attempted, optional failures remain visible and non-blocking; required failures and uncertain execution retain their existing failure rules.

Entering `REPAIR` reserves a round; issuing its first assignment consumes that reservation. If reassessment interrupts the gap, reuse the reserved round even at the configured limit. A round with an issued repair assignment is never refunded. For isolated candidates, passing validation alone does not mark provisional findings fixed: successful publication and verification of the checkout must also complete. A failed publication keeps those findings provisional, with validation evidence and the application journal retained for recovery.

Triage receives `sourceChanges` as data. Use `actionable` for remaining problems, `rejected` for unsupported findings, and `needs-validation` when newer edits appear to resolve a finding without matching controller validation. Required checks must pass before those provisional findings become `fixed`; failed checks cannot be retried unchanged through that disposition. Prior reports retain their original fingerprints and cannot form the new terminal quorum. Fresh validation and two complete reports on the resulting scope remain required. Counters, finding identities, prior evidence, and index contents are preserved. An updated preservation baseline also prevents explicit original-state recovery from discarding accepted external edits.

The full before/after snapshots, reports, and superseded proposal remain in the reconciliation record. Assignment context is limited to 128 entries per array and 64 KiB overall, with exact counts and explicit truncation. Omitted paths are not evidence of unchanged content.

Reconciliation that invalidates check evidence is bounded to three accepted snapshots per run. Validation changes assessed as leaving every completed check applicable do not consume that budget. Git/index or visibility-policy changes, source drift during application or isolated validation, unstable captures, and unresolved backup obligations still stop advancement. `SCOPE_CHANGED` is a controller outcome, not a reason to abandon the conversation: inspect its changed paths and retained evidence, assess which findings still apply, and explain the concrete conflict and safe continuation. Do not reset budgets, fabricate fresh review evidence, edit controller state, or silently launch discovery again.

At the limit, changes observed after one checkout validator completes still receive an applicability assessment. If they invalidate check evidence, the controller stops before executing another command; another source edit while that assessment is pending cannot extend the budget. The changed-file summary includes accepted receipt and concurrent edits as well as repairs. On unsuccessful runs, retained index changes also flag the staging handoff even when no working-tree bytes changed.

## Source and application guards

A terminal verdict with a pending retained-checkout observation is not settled. Status keeps `waiting` true, and new-run admission, release, and pruning refuse it until resume records that observation. A crash between the verdict and capture cannot waive this obligation.

Before publishing a checkout assignment, preparation verifies its source and Git metadata against the accepted snapshot, including after interruption. The same check runs before resuming a persisted external command that has no launch record or claim. Changed inputs stop as `SCOPE_CHANGED` before dispatch; the unstarted command is cancelled without execution, and the changes remain visible. They cannot silently become the assignment's starting baseline. An unchanged checkout resumes the same prepared assignment without another attempt. A recorded launch means execution may already be underway even before a claim appears; those jobs retain the existing settlement and reconciliation rules.

Default assignments use the actual checkout. Review and triage are read-only; repair may edit source and returns `workspaceEdits`. While a direct repair is pending, polling leaves its assignment intact instead of treating its own edits as external drift. At submission the controller checks attribution and Git metadata, records the changed files, and validates them in place. Concurrent changes outside the repair attribution list are preserved, recorded separately, and included in fresh validation/review without another repair round. The controller cannot identify which process wrote a shared-checkout file. A failed repair that already changed source or the index stops with those edits retained; it is not retried from an imaginary clean baseline. Explicit errors, worker loss, and blocked cleanup record observed changed paths and Git metadata drift in the outcome. After owned processes settle, failed checkout operations also persist their observed source in `snapshots/stopped-checkout.json`, with content in the existing blob store. Status exposes `retainedCheckout` and includes its paths in re-staging guidance. Every unsuccessful terminal run records the actual checkout against its last accepted baseline, regardless of assignment role or writer. This includes review/triage failures, failed repairs, and uncertain validation. Observation failures are explicit; neither observations nor successful process cleanup replace the last accepted baseline or promote a failed verdict. Inspect and reconcile the visible work. Outside its journaled per-round publication, the controller never changes the index; it never rolls back source files automatically.

Explicitly isolated assignments retain private copies and bounded retries; inline `edits` require unchanged assignment source. All assignments preserve Git metadata. Ignored build/cache outputs are allowed and do not count as source mutations or required-validation evidence. Other scratch files belong outside the repository. Uncertain executions stop without replay. Checkout source changes outside an active repair are reconciled; unsafe or unclassifiable drift remains `SCOPE_CHANGED`.

Validation receives EOF on stdin; JSON stdin is reserved for provider assignments. Waiting on a claimed command reads job metadata, not source inventories. Full source and fingerprint guards run before starting unclaimed work, consuming results, applying changes, and terminal decisions. Drift during a running command is assessed at its result or worker-loss boundary, not continuously polled.

An unstaged tracked-file replacement such as `tool` becoming `tool/index.sh` is captured as deletion of the old tracked file plus the replacement tree's included files. Copies preserve those contents and the original index; directories are not regular-file repair destinations. A workspace repair that introduces a file-to-directory conversion is rejected; direct edits remain in place, while explicitly isolated attempts fail before publication and retries receive a fresh copy. Attribution diagnostics identify ignored or unmanaged paths separately from unchanged paths and explain how to keep generated outputs outside the candidate.

Repository copies pin supported Git normalization settings, local/global/system attributes, and ignore policy for each initialized repository. Their staged and unstaged diffs must match the saved source before review. Inherited Git repository/index/object redirection is removed. Configured executable filter or text-conversion attributes are unsupported and fail explicitly; the controller does not transplant arbitrary Git configuration or provision conversion tools. Git policy changes participate in the source guard.

Validation executes the pinned commands against the actual candidate, in the existing checkout by default. Commands may write ignored build outputs and normal external caches. Tracked receipt and state-file changes in checkout mode retain the completed command result and enter local triage. Triage inspects every intervening change and the check dependencies, returning `validationImpact` as `unaffected` or `rerun` for each completed check; a path name alone cannot establish irrelevance. The controller records accepted reuse separately in `validationReuse`, bound to the new fingerprint and source hash, without changing the original execution record. It reruns only invalidated checks and continues unstarted checks. Reused failed results still require failure diagnosis; uncertain executions cannot be reused or replayed. Fresh final review covers the resulting checkout. Staged changes and visibility-policy changes still stop with specific evidence. The controller never installs dependencies. Known-not-started startup failures, including log creation and process launch, allow one recorded infrastructure retry. Signal-terminated commands are failed checks for diagnosis, not automatically infrastructure failures. Required checks are non-waivable obligations: triage may propose a counted repair or report a blocker, but rejection and severity filtering cannot authorize another unchanged failing validation cycle. Success requires a `succeeded` outcome, exit zero, and no error or termination signal. Timeout and cancellation remain failures even if a signal handler exits zero. Validation stdout uses a bounded 8 MiB log plus a 16 Ki-character tail, with truncation disclosed; verbose output does not kill the check. Short writes are completed; zero-progress writes and log write/close errors after command launch stop without replay. Structured provider reports retain their separate 2 MiB transport limit.

Application rechecks each destination and moves an existing file to a journal-owned backup before publishing its replacement through exclusive creation. It never renames a candidate over a live destination. A concurrent new destination stops publication without overwriting it; displaced inodes remain recoverable, including writes through already-open descriptors. Backups and targets must share a filesystem. Recovery handles the interruption between displacement and publication, during which a path can be absent. The journal retains before/after content and displaced files. There is no automatic rollback over concurrent work and no claim of a multi-file transaction or exclusive ownership against unrelated editors.

The same-filesystem requirement is checked before run allocation/review, on source guards, and for every destination in a batch before any file is published. Cross-filesystem linked worktrees or mounted destinations stop with `UNSUPPORTED_REPOSITORY`; they do not proceed to a partial repair or get mislabeled as source drift.

Application, failure cleanup, resume, and new-run admission use the same temporary-content verification and recovery checks. Existing candidates are never truncated; only verified images may be reused or removed. Changed or uninspectable temporaries are retained in `applicationRecovery.retainedTemporaries`. Missing displaced replacement destinations and changed backups are reported in `applicationRecovery.unresolvedPaths`. Until these obligations are resolved, a new run is refused even after a terminal outcome. Recover retained work explicitly and resume; the controller will not automatically restore a path that another editor may have deleted after publication. Backups and unrelated files remain preserved.

Successful publication appends its displaced-file records to `completedApplications` in the same durable update that clears the pending apply. These records protect late writes through old descriptors across every repair round. Completed records check backups, not current destinations, which later repairs or user edits may legitimately change. Changed, missing, uninspectable, or unjournaled backups prevent convergence, settlement, admission, release, and pruning. A historical terminal verdict is not rewritten after a later mutation; status exposes the new recovery obligation and admission is refused. These are checkpoint checks, not exclusive locks against unrelated writers.

Private repository copies use an empty Git initialization template and explicitly create their required administrative directories. Every copy-preparation Git command disables hooks with `-c core.hooksPath=/dev/null`; each root/submodule copy also stores that local policy for subsequent Git operations. User templates and globally configured hooks cannot execute during preparation. The original checkout and global hook configuration remain untouched; pinned source comparison attributes and ignore policy are restored separately.

Assignment agents do not write the source index. In `--commit-mode none`, the controller also leaves it unchanged; per-round mode has a separate [journaled commit publication boundary](commits.md#publication-and-recovery). Its guard compares staged OIDs, paths, modes, stages, and semantic flags, not cached inode/mtime fields. Ordinary `git status` refreshes are allowed in source and reviewer copies; staging changes are not. Preserve the original index and HEAD without treating Git's harmless internal cache updates as source edits.

Direct checkout execution is cooperative, not a sandbox for adversarial model code. Native reviewers must remain read-only; the controller detects changes to source and assignment copies. Both platform sandboxes confine validation writes, but read-only host files remain visible. Non-UTF-8 paths, unmerged indices, and symlink repairs fail explicitly. Regular source files are streamed through capture, copying, and integrity checks within the aggregate storage budgets; files read for validation-command discovery retain a separate 32 MiB parsing limit. Git metadata path components are rejected regardless of case, including on case-insensitive macOS volumes. Snapshots and application do not manage ignored files; checkout validation may write ignored outputs as part of the existing workflow. Pre-existing excluded and submodule files participate in mutation guards even though they are outside repair scope.

## Artifacts and handoff

If retained checkout capture or staging inspection fails, status still returns the saved outcome and recovery evidence. `restagingInspectionError` explains the inspection failure, and `indexNeedsRestaging` is conservatively true, even when capture could not enumerate changed paths; inspect the checkout before staging rather than treating that hint as a verified index comparison.

Version-14 `run.json` is authoritative workflow metadata. It pins the workspace-edit repair contract, role-specific assignment authority, `options.fixMode`, `options.commitMode`, and the complete declarative `fixPolicy` text at initialization; older controllers must not resume it without these requirements. Large immutable inventories use `$manifest` references into `manifests/`; their file entries reference SHA-256 content in `blobs/`. Resume loads and verifies inventories only when needed, so polling does not read or rewrite them. `events.jsonl` and `validation.json` remain projections reconstructed from the run. The run also contains contracts, reports, assignments, snapshots, patches, validation logs, and displaced-file `backups/`. `resources/` durably records copy and scratch ownership before allocation, including candidate-inspection and validation copies at the external `workspaceRoot`. Assignment identity and counters are saved before preparation; interrupted preparation resumes the same assignment without another provider attempt. Resume reconciles abandoned reservations and repeats pending deletion safely. Result consumption and cleanup responsibility are saved before deleting completed copies; source snapshots remain reconstructible from manifests and blobs. Snapshots retain each repository's Git object format and comparison policy, including initialized submodules. State uses atomic replacement, durable writes, and private permissions. Keep the record for resume and diagnosis; it includes source contents and provider transcripts. Older runs require the controller that created them and are not silently migrated, reinterpreted as source drift, or restarted. This run-format version is separate from the plugin release version. The controller publishes local round commits only in per-round mode; it does not push or deploy.
